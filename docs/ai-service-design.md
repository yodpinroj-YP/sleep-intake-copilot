# ออกแบบ AI Summarization Service ให้ "แม่นยำ รอบคอบ ซื่อสัตย์ และปลอดภัย" สำหรับ Sleep Intake Copilot

ตอบคำถาม: จะทำอย่างไรให้ AI ที่ช่วยแพทย์สรุปประวัติการนอนหลับ **ต่างจาก** การที่ผู้ป่วยไปถาม ChatGPT/Claude เองที่บ้าน

---

## หัวใจของปัญหา: ทำไม "ผู้ป่วยถาม AI เอง" ถึงอันตรายกว่า

| | ผู้ป่วยถาม AI เอง (เช่น ChatGPT) | AI service ใน Sleep Intake Copilot (ที่ควรเป็น) |
|---|---|---|
| ข้อมูลที่ AI เห็น | คำบรรยายของผู้ป่วยเอง ไม่ครบ ไม่เป็นระบบ | ข้อมูลโครงสร้างจากแบบสอบถามมาตรฐาน (ESS, STOP-BANG ฯลฯ) ที่คำนวณคะแนนแบบ deterministic ไว้แล้ว |
| ใครเป็นคนตัดสินใจสุดท้าย | ผู้ป่วยเชื่อคำตอบ AI ตรงๆ อาจไม่ปรึกษาหมอ | แพทย์เท่านั้นที่ตัดสินใจ — AI แค่ช่วยจัดเรียงให้อ่านง่ายขึ้น |
| ขอบเขตงานของ AI | ตอบได้ทุกเรื่อง รวมถึง "วินิจฉัย" หรือ "แนะนำการรักษา" | ทำได้แค่ "สรุป/จัดระเบียบข้อมูลที่มีอยู่แล้ว" ห้ามวินิจฉัยหรือแนะนำการรักษาเด็ดขาด |
| ตรวจสอบย้อนหลังได้ไหม | ไม่ได้ ไม่มีบันทึกว่าถามอะไรตอบอะไร | ทุกครั้งที่ AI ทำงานต้องถูกบันทึกลง `ai_processing_logs` พร้อม input/output/เวอร์ชันโมเดล |
| มีคนตรวจสอบก่อนใช้จริงไหม | ไม่มี | ต้องผ่าน `pending_review` → แพทย์ approve/reject ก่อนเสมอ (มีอยู่แล้วในระบบคุณ) |

สรุปหลักการที่ต้องยึดตลอด: **AI ในระบบนี้เป็น "เลขาที่ช่วยจัดระเบียบแฟ้ม" ไม่ใช่ "ที่ปรึกษาที่ตอบคำถามการแพทย์"** — งานของมันคือหยิบข้อมูลที่มีอยู่แล้ว (ที่คำนวณแบบกฎตายตัวไปแล้ว) มาเรียบเรียงให้แพทย์อ่านเร็วขึ้น ไม่ใช่การสร้างความรู้ใหม่หรือความเห็นใหม่

---

## 6 หลักการออกแบบ (นำไปใช้ตอนสร้างจริงใน Phase 3)

### 1. จำกัดสิ่งที่ AI "เห็น" ให้เหลือแค่ข้อมูลที่มีโครงสร้างเท่านั้น

- ห้ามส่ง free-text ทั้งหมดที่ผู้ป่วยพิมพ์ตรงๆ ให้ AI คิดเองแบบเปิดกว้าง
- Input ที่ส่งให้ AI ควรเป็น **เฉพาะ**: คำตอบแบบสอบถาม (`intake_responses`), คะแนนที่คำนวณไว้แล้ว (`questionnaire_scores`), และ safety flag ที่ระบบตรวจพบไปแล้ว (`safety_flags`) — ทั้งหมดนี้คำนวณด้วยโค้ด rule-based ที่ตรวจสอบได้ ไม่ใช่ AI เดา
- AI จึงไม่มีโอกาส "มโน" ตัวเลขคะแนนหรือ flag ขึ้นมาเอง เพราะตัวเลขเหล่านั้นคำนวณเสร็จก่อนถึงมือ AI แล้ว หน้าที่ AI มีแค่ "อธิบายเป็นภาษาที่อ่านง่าย"

### 2. บังคับ output ให้เป็นโครงสร้างตายตัว ไม่ใช่ความเรียงอิสระ

แทนที่จะให้ AI เขียนพารากราฟยาวๆ อิสระ ให้บังคับ (ผ่าน JSON schema / structured output ของ LLM API) ว่าต้องตอบเป็นหัวข้อคงที่ เช่น:

```
1. อาการหลักที่ผู้ป่วยแจ้ง (สรุปจาก chief_complaint)
2. ผลคะแนนแบบสอบถาม (ต้องอ้างอิงตัวเลขจริงจาก questionnaire_scores เท่านั้น)
3. Safety flag ที่ตรวจพบ (ต้องอ้างอิงจาก safety_flags เท่านั้น ห้ามเพิ่มเอง)
4. ประเด็นที่แนะนำให้แพทย์ซักถามเพิ่ม (ห้ามใส่คำวินิจฉัยหรือชื่อโรค)
5. ข้อมูลที่ไม่พอ/ไม่ชัดเจน (ถ้ามี ให้ระบุตรงๆ ว่า "ข้อมูลไม่เพียงพอสำหรับ...")
```

ข้อดี: แพทย์กวาดตาอ่านได้เร็ว, ตรวจสอบง่ายว่า AI พูดตรงกับข้อมูลจริงไหม, และ AI ไม่มีพื้นที่ให้ "แต่งเรื่อง" นอกกรอบ

### 3. เขียน System Prompt ที่ "ห้ามวินิจฉัย ห้ามเดา ห้ามเกินข้อมูล" อย่างชัดเจน

ตัวอย่างแนวทาง system prompt (จะช่วยเขียนจริงตอนถึง Phase 3):

> คุณเป็นผู้ช่วยจัดระเบียบข้อมูลให้แพทย์เฉพาะทางการนอนหลับ หน้าที่ของคุณคือสรุปข้อมูลที่ให้มาให้กระชับ **ห้ามวินิจฉัยโรค ห้ามแนะนำการรักษา ห้ามเพิ่มข้อมูลที่ไม่มีอยู่ในข้อมูลที่ได้รับ** หากข้อมูลไม่พอให้สรุปประเด็นใดประเด็นหนึ่ง ให้ระบุว่า "ข้อมูลไม่เพียงพอ" แทนการเดา ทุกตัวเลขที่คุณอ้างถึงต้องตรงกับตัวเลขในข้อมูลที่ได้รับเป๊ะๆ

หลักการ: **AI ควรถูก "ตีกรอบ" ให้แคบที่สุดเท่าที่งานยังมีประโยชน์อยู่** ยิ่งกรอบแคบ ยิ่งควบคุมความเสี่ยงได้มาก

### 4. Deterministic layer ต้องมาก่อนเสมอ และ AI ห้ามเถียงมัน

- คะแนนแบบสอบถามและ safety flag ต้องคำนวณด้วยโค้ดกฎตายตัว (มีอยู่แล้วในแผน Phase 1) **ก่อน** ที่จะส่งให้ AI เห็น
- AI มีหน้าที่แค่ "อธิบาย" ผลลัพธ์เหล่านั้น ไม่ใช่ "คำนวณใหม่" หรือ "ประเมินใหม่"
- ถ้า AI เขียนอะไรที่ขัดแย้งกับ safety flag ที่ระบบตรวจพบ (เช่น ระบบ flag ว่า "เสี่ยงสูง" แต่ AI สรุปว่า "ไม่น่ากังวล") — ต้องมีการตรวจสอบอัตโนมัติง่ายๆ (เทียบคำสำคัญ) และปฏิเสธไม่แสดงผล AI นั้น ให้ขึ้นเป็น error แทนที่จะให้แพทย์เห็นข้อความที่ขัดกันเอง

### 5. มนุษย์ต้องเป็นด่านสุดท้ายเสมอ (มีโครงสร้างนี้อยู่แล้ว — ต้องรักษาไว้)

- ทุก summary เกิดเป็น `pending_review` เท่านั้น ไม่เคยกลายเป็นส่วนหนึ่งของ record ผู้ป่วยจนกว่าแพทย์จะกด approve
- ผู้ป่วย **ไม่ควรเห็น** AI summary โดยตรงเลย (ต่างจากการถาม AI เองที่ผู้ป่วยเห็นคำตอบทันที) — นี่คือความต่างสำคัญที่สุดข้อหนึ่ง: AI พูดกับแพทย์ ไม่ได้พูดกับผู้ป่วยตรงๆ แพทย์เป็นคนกรองอีกชั้นก่อนสื่อสารกับผู้ป่วย
- ควรมีปุ่ม/ช่องให้แพทย์ "แก้ไข" summary ก่อน approve ได้ ไม่ใช่แค่ approve/reject แบบ all-or-nothing

### 6. บันทึกทุกอย่างเพื่อตรวจสอบย้อนหลังได้ (accountability)

- `ai_processing_logs` (มีตารางนี้อยู่แล้ว) ต้องเก็บ: input ที่ส่งไป, output ที่ได้กลับมา, เวอร์ชันโมเดลที่ใช้, เวลาที่เรียก, และผลการ approve/reject ของแพทย์
- สิ่งนี้สำคัญมากถ้าเกิดปัญหาภายหลัง (เช่น แพทย์ approve summary ที่ผิดพลาด) จะได้ตรวจสอบย้อนกลับได้ว่าเกิดจากอะไร — เป็นทั้งเรื่องความปลอดภัยและเรื่องกฎหมาย/PDPA

## กระบวนการก่อนเปิดใช้จริง (สำคัญไม่แพ้ตัวโค้ด)

1. **ทดสอบกับเคสสมมุติที่รู้คำตอบล่วงหน้าก่อน** — สร้าง mock intake session 10-20 แบบ (มีทั้งเคสเสี่ยงสูง/ต่ำ/ข้อมูลไม่ครบ) แล้วเช็คว่า AI สรุปตรงกับที่ควรจะเป็นไหม ก่อนให้แพทย์จริงเห็น
2. **ให้หมอ/พยาบาลจริง 2-3 คนทดลองอ่าน AI summary เทียบกับข้อมูลดิบ** แล้วถามตรงๆ ว่า "อ่านแล้วเข้าใจตรงกับข้อมูลจริงไหม มีอะไรที่ทำให้เข้าใจผิดไหม" — นี่คือ Phase 6 (Testing) ที่ต้องทำคู่กับ Phase 3 ไม่ใช่แยกกัน
3. **เตรียมแผนสำรองเมื่อ AI ล้มเหลว** — ถ้า LLM API เรียกไม่สำเร็จ/timeout ต้อง**ไม่แสดง summary ที่ผิด** ให้ขึ้นข้อความว่า "ยังไม่มีสรุปจาก AI สำหรับเซสชันนี้" ดีกว่าเสี่ยงแสดงข้อมูลผิด
4. **ปรึกษาฝ่ายจริยธรรม/กฎหมายของโรงพยาบาลก่อนใช้กับผู้ป่วยจริง** (ตรงกับ Phase 5 ในแผนงานเดิม) — โดยเฉพาะประเด็น "AI ช่วยสรุปข้อมูลทางคลินิก" อาจต้องแจ้งผู้ป่วยและขอ consent ว่ามีการใช้ AI ช่วยประมวลผลข้อมูลของเขา

## สรุปสั้นๆ

ความต่างที่แท้จริงระหว่าง "ผู้ป่วยถาม AI เอง" กับ "AI service ในระบบนี้" ไม่ได้อยู่ที่ตัวโมเดล AI ที่ใช้ (จะใช้ LLM ตัวเดียวกันก็ได้) แต่อยู่ที่ **กรอบและกระบวนการรอบตัวมัน**: จำกัดข้อมูลที่เห็น, บังคับรูปแบบคำตอบ, ห้ามวินิจฉัย, ให้แพทย์เป็นด่านสุดท้ายก่อนถึงผู้ป่วย, และบันทึกทุกอย่างเพื่อตรวจสอบย้อนหลังได้ — นี่คือสิ่งที่ทำให้มันน่าเชื่อถือและปลอดภัยกว่า ไม่ใช่ตัว AI ที่ "ฉลาดกว่า"

เมื่อพร้อมจะเริ่ม Phase 3 จริง แนะนำให้เริ่มจากตัวเลือก LLM provider (เช่น Claude API ผ่าน Anthropic โดยตรง เพราะควบคุมเรื่อง server-only API key และ structured output ได้ง่าย) แล้วค่อยเขียน route ทีละขั้นตามหลักการข้างต้น — ยินดีช่วยลงมือเขียนโค้ดจริงเมื่อพร้อมครับ
