# Sleep Intake Copilot — สิ่งที่พบหลังอ่านโค้ดและ schema ใหม่ทั้งหมด

เอกสารนี้เขียนหลังจากอ่าน `0001_init.sql` ทั้ง 401 บรรทัด + service layer + API routes ใหม่ทั้งหมด
มีทั้ง **ข่าวดีที่คุณอาจยังไม่รู้** และ **ปัญหาที่ต้องรู้ก่อนจะเดินต่อ**

---

## 1. ข่าวดี: schema ของคุณดีกว่าที่ผมเคยประเมินไว้มาก

ในเอกสารก่อนหน้า ผมประเมิน "AI summarization = 0%" ซึ่ง**ต่ำเกินไป** เพราะพอกลับไปอ่าน SQL จริง พบว่าตาราง `clinician_summaries` ถูกออกแบบมารองรับหลักการ "AI ต้องตอบเป็นโครงสร้าง ไม่ใช่ความเรียงอิสระ" ไว้ตั้งแต่แรกแล้ว:

| คอลัมน์ที่มีอยู่แล้ว | หมายถึงอะไร |
|---|---|
| `key_symptoms` (jsonb) | อาการสำคัญ — เป็น list ไม่ใช่ prose |
| `important_negatives` (jsonb) | สิ่งที่ผู้ป่วย "ไม่มี" ซึ่งสำคัญทางคลินิก |
| `missing_information` (jsonb) | AI ต้องบอกเองว่าข้อมูลตรงไหนไม่พอ |
| `needs_verification` (jsonb) | จุดที่ AI ไม่มั่นใจ ต้องให้แพทย์ตรวจสอบ |
| `version` (int, unique กับ session) | สร้าง summary ใหม่ได้โดยไม่ลบอันที่แพทย์ review ไปแล้ว |
| `model` (text) | บันทึกว่าโมเดลไหนสร้าง — ตรวจสอบย้อนหลังได้ |
| `reviewer_notes` | แพทย์เขียนหมายเหตุตอน review ได้ |

**แปลว่า**: หลักการ "บังคับ output เป็นโครงสร้าง + AI ต้องซื่อสัตย์ว่าอะไรไม่รู้" ที่ผมเสนอไปเมื่อวาน ไม่ต้องแก้ schema เลย — มีที่รองรับครบแล้ว แค่ยังไม่มีโค้ดที่เขียนลงไป

เรื่องดีอื่นๆ ที่พบ:
- `intake_sessions` มี `height_cm`, `weight_kg` และ **`bmi` เป็น generated column** (คำนวณอัตโนมัติในฐานข้อมูล) → รองรับ STOP-BANG ข้อ "B" (BMI > 35) ไว้แล้ว
- `intake_responses` มี `source = 'ai_extracted'` + `extraction_confidence` → รองรับกรณี AI ช่วยแปลงข้อความอิสระเป็นคำตอบมีโครงสร้าง พร้อมเก็บระดับความมั่นใจ
- `src/lib/supabase/admin.ts` (service-role client) มีอยู่แล้ว → ซึ่ง**จำเป็นมาก** สำหรับ Phase 1 (เหตุผลอยู่ข้อ 2)

## 2. ปัญหาที่ชัดที่สุด: 4 ใน 7 ตารางไม่มีทางเขียนข้อมูลลงไปเลย

นี่คือคำอธิบายที่ตรงที่สุดว่า "เหลืออะไรต้องทำ":

| ตาราง | อ่านได้ | เขียนได้ | มีโค้ดเขียนจริงไหม |
|---|---|---|---|
| `profiles` | ✅ | ✅ (trigger อัตโนมัติ) | ✅ มี |
| `intake_sessions` | ✅ | ✅ | ✅ มีครบ CRUD |
| `intake_responses` | ✅ | ✅ (RLS อนุญาตผู้ป่วยแล้ว) | ❌ **ไม่มีโค้ดเขียน** |
| `questionnaire_scores` | ✅ | ⚠️ service-role เท่านั้น | ❌ **ไม่มีโค้ดเขียน** |
| `safety_flags` | ✅ | ⚠️ service-role เท่านั้น | ❌ **ไม่มีโค้ดเขียน** |
| `clinician_summaries` | ✅ | ⚠️ review ได้เท่านั้น | ❌ **ไม่มีโค้ดสร้างแถวใหม่** |
| `ai_processing_logs` | ✅ | ⚠️ service-role เท่านั้น | ❌ **ไม่มีโค้ดเขียน** |

**จุดสำคัญที่ต้องเข้าใจ**: `questionnaire_scores` กับ `safety_flags` **ตั้งใจ**ไม่ให้ client เขียนได้ (ไม่มี insert policy สำหรับ `authenticated` เลย) เพราะเป็นข้อมูล deterministic ที่ต้องเชื่อถือได้ 100% — ถ้าปล่อยให้เบราว์เซอร์เขียนได้ ผู้ป่วยแก้คะแนนตัวเองได้

ดังนั้นตอนทำ Phase 1 **คะแนนต้องคำนวณและบันทึกฝั่ง server ด้วย service-role client เท่านั้น** (ผ่าน `src/lib/supabase/admin.ts` ที่มีอยู่แล้ว) ห้ามคำนวณในเบราว์เซอร์แล้วส่งคะแนนมาบันทึก — นี่เป็นกับดักที่คนมักพลาด

## 3. เรื่องที่อาจบล็อกคุณและยังไม่มีใครเตือน: แบบสอบถามมีลิขสิทธิ์

นี่คือข้อมูลที่ผมคิดว่ามีประโยชน์ที่สุดในเอกสารนี้ เพราะมันไม่ใช่เรื่องโค้ด แต่บล็อกการใช้จริงในโรงพยาบาลได้

**ESS (Epworth Sleepiness Scale)** — เว็บไซต์ทางการระบุชัดว่า *"A license is required to use the ESS or the ESS-CHAD, whether or not a license fee is payable"* คือ **ต้องขอ license เสมอ ไม่ว่าจะต้องจ่ายเงินหรือไม่** บริหารจัดการโดย Mapi Research Trust (ฝรั่งเศส) ผ่านแพลตฟอร์ม ePROVIDE — บางกลุ่มผู้ใช้ต้องจ่าย บางกลุ่มไม่ต้อง ขึ้นกับลักษณะการใช้

**ISI (Insomnia Severity Index)** — เผยแพร่ผ่าน Mapi Research Trust / ePROVIDE เช่นเดียวกัน คือต้องขออนุญาตผ่านช่องทางเดียวกัน

**STOP-BANG** — ลิขสิทธิ์อยู่กับ University Health Network (Toronto) เว็บทางการคือ stopbang.ca (ผมเข้าถึงหน้า license โดยตรงไม่ได้เพราะปัญหาใบรับรอง SSL ของเว็บเขาเอง) โดยทั่วไปอนุญาตให้ใช้ทางการศึกษา/ไม่แสวงกำไรได้ แต่**การใช้เชิงพาณิชย์ต้องขออนุญาต** — ต้องยืนยันกับเจ้าของสิทธิ์โดยตรงก่อนใช้จริง

### ทำยังไงไม่ให้เรื่องนี้บล็อกคุณตอนนี้

แยกให้ชัดระหว่างสองอย่าง:
- **ข้อความคำถามเป๊ะๆ** (item wording) → นี่คือสิ่งที่มีลิขสิทธิ์
- **วิธีคิดคะแนนและเกณฑ์แบ่งกลุ่ม** (scoring algorithm, cutoffs) → เป็นข้อเท็จจริงทางวิชาการที่ตีพิมพ์เปิดเผยทั่วไป

**คุณสร้าง scoring engine ได้เลยตอนนี้** โดยใช้ placeholder เช่น `ess_item_1` … `ess_item_8` แล้วค่อยเติมข้อความจริงเมื่อได้ license — โครงสร้างโค้ด ฐานข้อมูล และการทดสอบทั้งหมดไม่ต้องแก้เลย

สำหรับงานส่งอาจารย์/เดโม โดยทั่วไปไม่มีปัญหา แต่**ถ้าจะใช้จริงในโรงพยาบาล ต้องเคลียร์เรื่องนี้ก่อน** และควรเริ่มติดต่อแต่เนิ่นๆ เพราะกระบวนการขอ license ใช้เวลาหลายสัปดาห์

## 4. โครงสร้างคะแนน (ใช้ออกแบบ scoring engine ได้เลย)

> ตัวเลขเหล่านี้เป็นเกณฑ์ที่ใช้อ้างอิงกันทั่วไปในวรรณกรรม — **ต้องให้แพทย์เฉพาะทางการนอนหลับยืนยันอีกครั้ง**ก่อนใช้จริง เพราะบางสถาบันใช้ cutoff ต่างกันเล็กน้อย

| เครื่องมือ | จำนวนข้อ | สเกลต่อข้อ | คะแนนรวม | การแบ่งกลุ่ม (ทั่วไป) |
|---|---|---|---|---|
| **ESS** | 8 | 0–3 (โอกาสเผลอหลับ) | 0–24 | ≤10 ปกติ / 11–14 เล็กน้อย / 15–17 ปานกลาง / 18–24 รุนแรง |
| **STOP-BANG** | 8 | ใช่/ไม่ใช่ (1/0) | 0–8 | 0–2 เสี่ยงต่ำ / 3–4 เสี่ยงปานกลาง / 5–8 เสี่ยงสูง |
| **ISI** | 7 | 0–4 | 0–28 | 0–7 ไม่มีนัยสำคัญ / 8–14 ระดับต่ำ / 15–21 ปานกลาง / 22–28 รุนแรง |
| **BERLIN** | 3 หมวด | — | — | ผลบวก ≥2 หมวด = เสี่ยงสูง OSA |

**STOP-BANG 8 ข้อคือ** (ตัวย่อ ไม่ใช่ข้อความคำถามที่มีลิขสิทธิ์): **S**noring (นอนกรน), **T**ired (ง่วงกลางวัน), **O**bserved apnea (มีคนเห็นหยุดหายใจ), **P**ressure (ความดันโลหิตสูง), **B**MI > 35, **A**ge > 50, **N**eck circumference > 40 ซม., **G**ender = ชาย

สังเกตว่า **3 ใน 8 ข้อ (B, A, G) คำนวณจากข้อมูลที่คุณเก็บอยู่แล้ว** — `intake_sessions.bmi` (generated column), `profiles.date_of_birth`, `profiles.sex` ไม่ต้องถามผู้ป่วยซ้ำ

## 5. Safety flags: ชุดเริ่มต้นที่แนะนำ + เรื่องที่ต้องระวังเป็นพิเศษ

`safety_flags` มี `severity` แค่ 2 ระดับ (`standard` / `urgent`) — เริ่มจากกฎง่ายๆ เหล่านี้พอ:

| flag_type | เงื่อนไข | severity | เหตุผล |
|---|---|---|---|
| `drowsy_driving` | ตอบว่าเคยเผลอหลับ/เกือบหลับขณะขับรถ | `urgent` | เสี่ยงอุบัติเหตุถึงชีวิต ต้องแจ้งแพทย์ทันที |
| `severe_sleepiness` | ESS ≥ 16 | `urgent` | ง่วงระดับอันตรายต่อการขับขี่/ทำงาน |
| `high_osa_risk` | STOP-BANG ≥ 5 | `standard` | ควรส่งตรวจ sleep study |
| `witnessed_apnea` | มีคนเห็นหยุดหายใจขณะหลับ | `standard` | อาการบ่งชี้ OSA ชัดเจน |
| `possible_cataplexy` | กล้ามเนื้ออ่อนแรงเฉียบพลันเวลามีอารมณ์ร่วม | `standard` | คัดกรอง narcolepsy |

### ⚠️ เรื่องที่ต้องคิดก่อนเขียนโค้ด: สุขภาพจิต

แบบสอบถามเรื่องการนอนไม่หลับ **จะทำให้ผู้ป่วยบางคนเล่าเรื่องภาวะซึมเศร้าหรือความคิดทำร้ายตัวเองออกมา** — insomnia กับ depression เกี่ยวข้องกันสูงมาก นี่ไม่ใช่กรณีสมมุติ แต่จะเกิดขึ้นจริงแน่นอนถ้ามีผู้ใช้จริง

สิ่งที่ต้องตัดสินใจ **ร่วมกับแพทย์/นักจิตวิทยา ไม่ใช่ตัดสินใจเองในโค้ด**:
1. ถ้าตรวจพบสัญญาณ ระบบจะ**แจ้งใครและภายในกี่นาที** — ถ้าผู้ป่วยกรอกแบบสอบถามตอนตี 2 ที่บ้าน ใครรับผิดชอบ?
2. หน้าจอจะ**แสดงอะไรให้ผู้ป่วยเห็นทันที** (เช่น เบอร์สายด่วนสุขภาพจิต 1323 ของกรมสุขภาพจิต)
3. **AI ต้องไม่เป็นคนตอบเรื่องนี้เด็ดขาด** — ต้องเป็น static content ที่แพทย์เขียนไว้ล่วงหน้า และต้องส่งต่อให้มนุษย์เสมอ

การตรวจจับด้วย keyword ล้วนๆ ไม่แม่นพอ (ทั้ง false positive และ false negative) — ทางที่ปลอดภัยกว่าคือใส่**คำถามคัดกรองตรงๆ ที่เป็นมาตรฐาน** (เช่น PHQ-2/PHQ-9 ซึ่งมีเกณฑ์ชัดเจน) แทนการให้โค้ดเดาจากข้อความอิสระ

## 6. ขอแก้คำแนะนำเดิมของผมเอง เรื่อง AI audit log

เมื่อวานผมเขียนว่า *"`ai_processing_logs` ต้องเก็บ input ที่ส่งไปและ output ที่ได้กลับมา"*

พอกลับไปอ่าน SQL จริง พบว่า schema **จงใจไม่เก็บ** และมีคอมเมนต์อธิบายเหตุผลไว้ด้วย — เพราะการเก็บ prompt/response เต็มๆ เท่ากับ**ทำสำเนาข้อมูลสุขภาพผู้ป่วยเพิ่มอีกชุด** ซึ่งขัดหลัก data minimization ของ PDPA

**การออกแบบที่ผมคิดว่าดีที่สุด (ไม่สุดโต่งทั้งสองทาง)**:
- ไม่ต้องเก็บ prompt/response ซ้ำ เพราะ `intake_responses` (input) และ `clinician_summaries` (output) **เป็น system of record อยู่แล้ว** — ตรวจสอบย้อนหลังได้จากสองตารางนี้
- ใน `ai_processing_logs` เก็บแค่ **metadata**: `model`, `latency_ms`, `status`, `error_message`, `session_id` (มีครบแล้วใน schema)
- เพิ่มสิ่งเดียวที่ยังขาด: **`prompt_version`** — เพื่อให้รู้ว่า summary แต่ละอันสร้างจาก prompt เวอร์ชันไหน เวลาแก้ prompt แล้วผลเปลี่ยน จะสืบย้อนได้ว่าเกิดจากอะไร

```sql
alter table public.ai_processing_logs
  add column if not exists prompt_version text;
```

นี่ได้ทั้งความสามารถตรวจสอบย้อนหลัง และไม่เพิ่มความเสี่ยงข้อมูลรั่ว

## 7. ตารางที่ยังขาดสำหรับเป้าหมาย "ใช้จริงในโรงพยาบาล"

| ตารางที่ต้องเพิ่ม | ทำไมต้องมี | จำเป็นตอนไหน |
|---|---|---|
| `patient_caregivers` | ผูกผู้ดูแล (ญาติ) กับผู้ป่วย — ไม่มีตารางนี้ role `caregiver` เกิดไม่ได้เลย | Phase 2 |
| `consents` | บันทึกว่าผู้ป่วยยินยอมอะไร เมื่อไหร่ เวอร์ชันข้อความยินยอมไหน — **PDPA บังคับ** | Phase 5 (แต่ออกแบบตั้งแต่ตอนนี้ได้) |
| `audit_log` | ใครเปิดดู/แก้ข้อมูลผู้ป่วยคนไหน เมื่อไหร่ — **ต่างจาก `ai_processing_logs` ที่บันทึกแค่การเรียก AI** | Phase 5 |

**`audit_log` คือช่องว่างที่ใหญ่ที่สุดสำหรับการใช้จริงในโรงพยาบาล** — ฝ่าย IT security ของโรงพยาบาลทุกแห่งจะถามหาสิ่งนี้เป็นอย่างแรก ว่า "ถ้าพยาบาลคนหนึ่งเปิดดูประวัติคนไข้ที่ไม่ใช่คนไข้ตัวเอง ระบบรู้ไหม" ตอนนี้คำตอบคือ **ไม่รู้** เพราะ RLS อนุญาตให้ clinician ทุกคนดูข้อมูลผู้ป่วยทุกคนได้ และไม่มีการบันทึกว่าใครดูอะไร

## 8. สิ่งที่ผมแนะนำให้ทำเป็นอย่างต่อไป (เจาะจงมาก)

**ทำ STOP-BANG ให้ครบวงจรทีละอันเดียวก่อน** — อย่าทำทั้ง 4 แบบสอบถามพร้อมกัน

เหตุผลที่เลือก STOP-BANG เป็นตัวแรก (ไม่ใช่ ESS):
1. **8 ข้อ ตอบ ใช่/ไม่ใช่** → UI ง่ายที่สุดที่เป็นไปได้ ไม่ต้องทำ slider หรือ scale
2. **3 ใน 8 ข้อดึงจากข้อมูลที่มีอยู่แล้ว** (BMI คำนวณอัตโนมัติในฐานข้อมูลแล้ว, อายุจาก `date_of_birth`, เพศจาก `sex`)
3. **การคิดคะแนนคือการบวกเลข** → เขียน test ได้ง่าย ตรวจสอบความถูกต้องได้ชัดเจน
4. เป็นเครื่องมือคัดกรอง OSA ที่ใช้บ่อยที่สุดในคลินิกการนอนหลับ → มีคุณค่าทางคลินิกจริง

ลำดับงาน 6 ขั้น (ทำตามลำดับ อย่าข้าม):

1. หน้าจอแบบสอบถาม 8 ข้อ → บันทึกลง `intake_responses` (ผู้ป่วยเขียนเองได้ RLS อนุญาตแล้ว)
2. เพิ่ม `height_cm` / `weight_kg` / `neck_circumference_cm` ในหน้าแรกของแบบสอบถาม
3. เขียนฟังก์ชันคิดคะแนนแยกเป็นไฟล์ล้วนๆ (pure function) ที่ไม่แตะฐานข้อมูลเลย → **ทดสอบได้ง่ายที่สุด**
4. สร้าง API route ที่ใช้ **service-role client** อ่าน `intake_responses` → คิดคะแนน → เขียนลง `questionnaire_scores`
5. กฎ safety flag ข้อแรกข้อเดียวก่อน: STOP-BANG ≥ 5 → เขียนลง `safety_flags`
6. แสดงผลคะแนน + flag บนหน้า dashboard ของแพทย์

**เสร็จ 6 ข้อนี้ = คุณจะมี pattern ครบทุกอย่างที่เหลือ** — ESS, ISI, BERLIN คือการทำซ้ำรูปแบบเดิม และ Phase 3 (AI) ก็แค่เพิ่ม route ที่อ่านสองตารางนี้แล้วเรียก LLM

---

## สรุปตัวเลขที่ปรับใหม่

จากเดิมที่ผมประเมินรวม ~12–15% ขอปรับเป็น **~18–20%** เพราะ schema รองรับงาน Phase 3 ไว้มากกว่าที่ผมนับไว้ตอนแรก (structured summary fields, versioning, service-role client, generated BMI column)

แต่ข้อสรุปหลักไม่เปลี่ยน: **โครงสร้างแข็งแรงแล้ว สิ่งที่ขาดคือ "เนื้อหาทางคลินิก" และ "เส้นทางเขียนข้อมูล" ไม่ใช่การออกแบบระบบ** ซึ่งเป็นข่าวดี เพราะงานที่เหลือส่วนใหญ่เป็นการเติมของลงในโครงที่วางไว้ดีแล้ว ไม่ใช่การรื้อ
