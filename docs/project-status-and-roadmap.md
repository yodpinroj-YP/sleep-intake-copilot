# Sleep Intake Copilot — สถานะโปรเจกต์ ณ วันนี้ และแผนงานถัดไป

**Live URL:** https://sleep-intake-copilot.vercel.app
**สถานะโดยรวม:** Working technical prototype — ใช้เดโมได้จริง แต่ยังห่างไกลจากระบบที่พร้อมใช้งานจริงในโรงพยาบาล

---

## ภาพรวมสั้นๆ ก่อน

สิ่งที่คุณมีตอนนี้คือ **โครงกระดูกทางเทคนิค (technical skeleton)** ที่ทำงานได้จริงครบวงจร (auth → database → CRUD → deploy) แต่ยังไม่มี "เนื้อหาทางคลินิก" ที่แท้จริง — ยังไม่มีแบบสอบถามจริง ยังไม่มี AI สรุปผลจริง ยังไม่มี role ของ caregiver/nurse แยกจาก patient/clinician และยังไม่ผ่านมาตรฐานความปลอดภัยข้อมูลสุขภาพใดๆ เลย

พูดตรงๆ คือ: **นี่คือ "บันไดขั้นแรก" ของโปรเจกต์ ไม่ใช่ครึ่งทาง** — งานส่วนที่ยากและสำคัญที่สุด (การออกแบบ clinical workflow จริง, ความปลอดภัยข้อมูลผู้ป่วย, และการยอมรับจากผู้ใช้จริงในโรงพยาบาล) ยังไม่ได้เริ่มเลย

## ความคืบหน้าโดยประมาณ (แยกตามด้าน)

| ด้าน | ความคืบหน้า | หมายเหตุ |
|---|---|---|
| โครงสร้างเทคนิคพื้นฐาน (auth, database, deploy) | **~70%** | ใช้งานได้จริง ผ่านการทดสอบ end-to-end แล้ว |
| Core clinical workflow (แบบสอบถาม, การให้คะแนน, safety flag) | **~10%** | มีแค่ schema รองรับ ยังไม่มีหน้าจอ/ตรรกะจริง |
| Multi-role สำหรับ patient / caregiver / nurse / doctor | **~15%** | ตอนนี้มีแค่ patient กับ clinician (รวม nurse+doctor เป็นก้อนเดียว) ไม่มี caregiver เลย |
| AI summarization จริง | **0%** | ยังไม่มีการเรียก LLM จริงเลย มีแค่ตารางรองรับผลลัพธ์ |
| ความปลอดภัย/มาตรฐานข้อมูลสุขภาพ (PDPA, audit, encryption) | **~5%** | มีแค่ RLS พื้นฐาน ยังไม่มี audit trail ที่ครบ ไม่มี compliance review |
| UX/UI สำหรับผู้ใช้จริง (responsive, ภาษาไทย, accessibility) | **~10%** | เป็น UI ขั้นต่ำสุดสำหรับเดโม ยังไม่ออกแบบเพื่อผู้ป่วย/พยาบาลจริง |
| การทดสอบ (unit test, QA, user testing) | **~5%** | มีแค่การทดสอบมือของคุณเอง ไม่มี automated test |
| การ integrate กับระบบโรงพยาบาล (HIS/EHR) | **0%** | ยังไม่ได้เริ่มคิดเลย |
| Pilot / การนำไปใช้จริงกับผู้ใช้จริง | **0%** | ยังไม่มีใครนอกจากคุณทดสอบ |

**ค่าเฉลี่ยรวมโดยประมาณ: ~12-15%** ของเป้าหมาย "เว็บแอปใช้งานจริงในโรงพยาบาล พร้อมผู้ใช้ patients, caregivers, nurses, sleep doctors"

(ตัวเลขนี้เป็นการประมาณคร่าวๆ เพื่อให้เห็นภาพเท่านั้น ไม่ใช่ตัวชี้วัดที่แม่นยำ)

## สิ่งที่ทำสำเร็จแล้ว ✅

1. Next.js + Supabase scaffold ทำงานได้จริง, build ผ่าน, deploy ขึ้น Vercel สำเร็จ
2. ฐานข้อมูล 7 ตารางที่ออกแบบมาสำหรับ domain นี้โดยเฉพาะ (ไม่ใช่ generic template) พร้อม Row Level Security ครบทุกตาราง
3. Auth (signup/login) ทำงานจริง มีการสร้าง profile อัตโนมัติพร้อม role
4. CRUD พื้นฐานครบ (Create/Read/Update/Delete) บน intake_sessions
5. แยกสิทธิ์ patient vs clinician ในระดับ database (RLS) และ UI เบื้องต้น
6. Deploy pipeline ที่ใช้งานได้จริง (GitHub → Vercel → Production, auto-redeploy เมื่อ push)

## สิ่งที่ยังไม่มี / ยังไม่ได้ทำ ❌

- **ไม่มีแบบสอบถามจริง** — ยังไม่มีหน้าจอให้ผู้ป่วยตอบคำถาม ESS/STOP-BANG/ISI/BERLIN เลย มีแค่ตารางรองรับผลคะแนน
- **ไม่มีตรรกะการให้คะแนน (scoring engine)** — `questionnaire_scores` ยังไม่มีโค้ดคำนวณคะแนนจริง
- **ไม่มีการตรวจจับ safety flag อัตโนมัติ** — `safety_flags` ยังไม่มี logic ที่ตรวจจับจากคำตอบจริง
- **ไม่มี AI จริง** — `clinician_summaries` ต้องใส่มือทาง database เท่านั้น ยังไม่มี route ที่เรียก LLM จริง
- **ไม่มี role caregiver** — ผู้ดูแลผู้ป่วย (เช่น ญาติ) ยังไม่มีที่ทางในระบบเลย
- **nurse กับ doctor ยังไม่แยกกัน** — ตอนนี้รวมเป็น `clinician` เดียว ทั้งที่ในโรงพยาบาลจริง สิทธิ์และหน้าที่ของพยาบาลกับแพทย์ต่างกันมาก
- **ไม่มี PDPA/ความปลอดภัยข้อมูลสุขภาพระดับที่ใช้ได้จริง** — ไม่มี audit log ครบ, ไม่มีการเข้ารหัสข้อมูลอ่อนไหวเพิ่มเติม, ไม่มี consent flow, ไม่มี data retention policy
- **ไม่มี automated test เลย** — เสี่ยงมากถ้าจะแก้โค้ดต่อไปโดยไม่มี test คุ้มกัน
- **ไม่มีการ integrate กับระบบโรงพยาบาล** — HIS/EHR, LINE OA แจ้งเตือน, หรือระบบนัดหมาย ล้วนยังไม่ได้คิด
- **ไม่มี legal/ethics review** — ระบบที่แตะข้อมูลสุขภาพและใช้ AI ช่วยวินิจฉัย ในไทยอาจเข้าข่ายต้องผ่านการพิจารณาจริยธรรมการวิจัย/มาตรฐานเครื่องมือแพทย์ (ถ้าจะใช้จริงในโรงพยาบาล)

## แผนงานถัดไป แบบ Step by Step

### Phase 1 — ทำ Core Clinical Workflow ให้ใช้งานได้จริง (ลำดับความสำคัญสูงสุด)
1. ออกแบบแบบสอบถามจริง (ESS, STOP-BANG อย่างน้อย 2 ชุดก่อน) เป็นหน้าจอ multi-step form
2. เขียนโค้ดคำนวณคะแนนแบบ deterministic (rule-based, ไม่ใช้ AI) แล้วบันทึกลง `questionnaire_scores`
3. เขียนกฎตรวจจับ safety flag ง่ายๆ ก่อน (เช่น "ง่วงขณะขับรถ" จากคำตอบ checkbox) บันทึกลง `safety_flags`
4. ทดสอบ flow เต็ม: ตอบแบบสอบถาม → เห็นคะแนน → เห็น safety flag ขึ้นถ้าเข้าเงื่อนไข

### Phase 2 — เพิ่ม Role ให้ครบตามผู้ใช้จริง
1. เพิ่ม role `caregiver` ใน `profiles` — ผู้ดูแลเห็นข้อมูลของผู้ป่วยที่ตัวเองผูกไว้เท่านั้น (ต้องมีตาราง "ความสัมพันธ์" เพิ่ม เช่น `patient_caregivers`)
2. แยก `clinician` เป็น `nurse` กับ `doctor` และกำหนดสิทธิ์ต่างกัน (เช่น nurse ดูได้แต่ approve summary ไม่ได้ ต้องเป็น doctor เท่านั้น)
3. ปรับ RLS policy ทุกตารางให้รองรับ role ใหม่

### Phase 3 — เชื่อม AI จริง
1. เลือกผู้ให้บริการ LLM (Anthropic, OpenAI ฯลฯ) และตั้งค่า API key อย่างปลอดภัย (server-only)
2. เขียน route ที่ดึงข้อมูล `intake_responses` + `questionnaire_scores` ของ session หนึ่ง ส่งให้ LLM สรุปเป็นภาษาที่หมออ่านง่าย แล้วบันทึกเป็น `clinician_summaries` สถานะ `pending_review`
3. ทดสอบว่าหมอ/พยาบาล approve/reject ได้จริงตาม flow ที่มีอยู่แล้ว

### Phase 4 — ปรับ UX/UI ให้ใช้งานได้จริงสำหรับผู้ป่วย
1. แปลทั้งระบบเป็นภาษาไทย (หรือรองรับสองภาษา)
2. ทำ mobile-responsive อย่างจริงจัง (ผู้ป่วยส่วนใหญ่ใช้มือถือ)
3. คำนึงถึง accessibility (ผู้สูงอายุ, ตัวหนังสือใหญ่, contrast ชัดเจน)

### Phase 5 — ความปลอดภัยและ Compliance
1. เพิ่ม audit log ให้ครบทุก action ที่แตะข้อมูลผู้ป่วย
2. ทำ consent flow (ผู้ป่วยต้องยินยอมก่อนให้ AI ประมวลผลข้อมูล)
3. ปรึกษาฝ่ายกฎหมาย/จริยธรรมของโรงพยาบาลเกี่ยวกับ PDPA และการใช้ AI ช่วยด้านคลินิก **ก่อน**จะมีข้อมูลผู้ป่วยจริงเข้าระบบ
4. พิจารณาว่าระบบนี้เข้าข่าย "เครื่องมือแพทย์ซอฟต์แวร์" ตามกฎหมายไทยหรือไม่ (ถ้าใช่ ต้องขึ้นทะเบียนกับ อย.)

### Phase 6 — Testing & QA
1. เขียน automated test (unit test สำหรับ scoring logic อย่างน้อย เพราะผิดพลาดมีผลทางคลินิก)
2. ทำ user testing กับพยาบาล/หมอจริง 2-3 คนก่อน (ไม่ใช่ผู้ป่วยจริง) เพื่อเก็บ feedback

### Phase 7 — Pilot กับผู้ใช้จริง (แบบควบคุม)
1. เริ่ม pilot กับข้อมูล synthetic หรือ mock patient ก่อน ไม่ใช่ผู้ป่วยจริง
2. ค่อยขยายเป็นการทดลองใช้จริงแบบมีการดูแลใกล้ชิดจากทีมแพทย์ (supervised pilot)
3. เก็บ feedback ปรับปรุงก่อนขยายผล

## ข้อควรระวังที่สำคัญที่สุดตอนนี้

> **อย่าเพิ่งใส่ข้อมูลผู้ป่วยจริงเข้าระบบนี้** จนกว่าจะผ่าน Phase 5 (ความปลอดภัย/compliance) เป็นอย่างน้อย เพราะตอนนี้ระบบยังไม่มีมาตรการปกป้องข้อมูลสุขภาพที่เพียงพอตามมาตรฐาน PDPA หรือมาตรฐานโรงพยาบาลทั่วไป การใช้กับข้อมูลจริงก่อนพร้อมอาจมีความเสี่ยงทั้งด้านกฎหมายและจริยธรรม

โปรเจกต์นี้ในตอนนี้เหมาะสำหรับ: งานส่งอาจารย์, เดโมแนวคิด (proof of concept), หรือฐานเริ่มต้นสำหรับพัฒนาต่อ — **ยังไม่เหมาะให้นำไปทดลองใช้กับผู้ป่วยจริงในโรงพยาบาล**
